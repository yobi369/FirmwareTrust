Release trust workbench

Run the complete signing and verification workflow with your own firmware file.

Browser session
01

Create your signing identity

Generate an Ed25519 key pair in this browser. Your private key is encrypted with a passphrase before it is downloaded.

Protect this passphrase. FirmwareTrust cannot recover it. The encrypted vault is unusable without it. Do not share the vault or passphrase.
02

Sign a firmware release

Select a firmware artifact and your encrypted private-key vault. The browser computes its digest and signs a canonical release manifest.

03

Verify a release independently

Verify the signature using a separately supplied public key, then recompute the firmware SHA-256 digest and compare its size.

New here? Load a self-contained sample release generated with a temporary in-memory key, then verify it and run the tamper test.

▣Privacy by design: cryptographic operations run in your browser. Firmware, manifests, passphrases and keys are not sent to a FirmwareTrust server. For sensitive environments, review the source code and use a trusted device.
THE WORKFLOW

From binary to verifiable evidence.

01 / IDENTITY

Establish a signer

Generate an Ed25519 key pair. Export the public key separately and protect the private key in a passphrase-encrypted vault.

02 / RELEASE

Bind metadata to bytes

Calculate SHA-256 and byte size, construct a canonical JSON manifest, and sign the manifest payload with the private key.

03 / VERIFICATION

Check against trust

Verify the signature against an independently supplied public key and recompute the artifact digest. Altered bytes or metadata fail verification.

SECURITY BOUNDARIES

Useful proof. Honest limits.

This M0 product demonstrates cryptographic release signing and integrity verification. A valid signature proves that the signed manifest matches a particular private key and artifact digest. It does not prove the firmware is safe, the signer is authorized, or a device enforces the result.

  • Not a secure-boot implementation or device-side verifier.
  • No device provisioning, anti-rollback, OTA deployment or fleet management yet.
  • Key revocation, rotation, organizational access controls and audit registry are roadmap work.
  • Production use requires independent security review, hardened key custody and target-specific validation.
